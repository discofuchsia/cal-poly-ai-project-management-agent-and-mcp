The problem

A lot of program management is information logistics.

Moving information

  • Chasing status across five tools and three time zones
  • Reconciling the tracker with what people actually said
  • Hunting for the blocked dependency before it bites
  • Rewriting the same facts for the team, then for leadership

Making calls

  • Choosing what to cut when the date is fixed
  • Negotiating trade-offs between teams
  • Having the hard conversation early
  • Owning the commitment

Agents are good at the left column. The right column is still the job.

Definitions

From chatbot to agent

Chatbot

Answers

Knows what it was trained on. Can't see your project.

Assists

Sees what you paste or open. You do every step.

Agent

Acts toward a goal

Plans, calls tools, reads results, and repeats until the goal is met. Asks before it changes anything.

you ask
"Are we going to make Friday? If not, what do I need to decide?"
Anatomy

An agent is a model in a loop, with tools.

  • Model does the reasoning and the writing
  • Tools let it read and change the real world
  • Context carries the goal, rules and history
  • Guardrails decide what it may do without asking

Model Context Protocol

MCP turns N × M integrations into N + M.

BEFORE · EVERY APP WIRES EVERY TOOL

3 agents × 4 tools = 12 custom integrations

AFTER · EVERYONE SPEAKS MCP

3 + 4 = 7 implementations, and any agent can use any tool

How it works

Hosts, clients, servers

Host

The agent app

Kiro, Claude Desktop, VS Code, your own app. Runs the model and decides when to call a tool.

Client

One per connection

Lives inside the host. Speaks JSON-RPC 2.0 to one server over stdio or HTTP.

Server

Wraps a system

Your tracker, repo, calendar or database. Publishes what the agent may do, with typed inputs.

Tools  actions the model can call: update_task

Resources  data the app can read in: files, records, schemas

Prompts  reusable templates the user can invoke

Open standard introduced by Anthropic in November 2024 and now supported across many agent hosts. Spec: modelcontextprotocol.io

On the wire

One tool call is two JSON messages.

HOST → SERVER

{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "analyze_risks",
    "arguments": {}
  }
}

The model chose this tool because its name, description and input schema came back from tools/list at startup.

SERVER → HOST

{
  "jsonrpc": "2.0",
  "id": 3,
  "result": {
    "content": [{
      "type": "text",
      "text": "{ \"risks\": [ {
        \"severity\": \"high\",
        \"type\": \"dependency\",
        \"task\": \"R-106\",
        \"critical_path\": true
      }, ... ] }"
    }]
  }
}

Under the hood

About 300 lines of Python. No framework.

pm_board_server.py · register a tool

TOOLS = {
  "analyze_risks": (
    tool_analyze_risks,
    "Deterministic risk scan: blocked, overdue,
     unassigned, blocked dependencies and
     overloaded people, sorted by severity.",
    {"type": "object", "properties": {}}),
  "update_task": (
    tool_update_task,
    "Change status or assignee, or add a note.
     Writes to the board; ask the human first.",
    {...}),
}
# stdin/stdout loop: initialize, tools/list, tools/call
for line in sys.stdin:
    handle(json.loads(line))

The most important design choice

Code computes the numbers.
The model makes the judgment.

Deterministic, in the MCP server

Overdue dates, story points, critical path, workload percentages. Same input, same answer, every run. Testable.

Probabilistic, in the model

Which risk matters most, how to phrase it for an exec, what decision to put in front of the TPM, what to ask next.

Ask a model to add up points and it can be confidently wrong. Ask it to explain points a tool added up, and it does that well.

Lessons from running agents on real work

Trust is designed in, not hoped for.

1

Agent proposes, human decides

Reads run freely. Every write shows the exact change and waits for approval.

2

Cite everything

Every claim points to a task ID or record, so a reviewer can check it in seconds.

3

Least privilege tools

Expose update_task, not run_sql. Narrow tools are safer and easier for the model to use correctly.

4

Say when evidence is thin

"I don't have enough data" is a valid answer. Make the agent say it instead of guessing.

5

Measure before you trust

Compare the agent's output against answers your experts labeled, before you rely on it.

6

Keep an audit trail

Log every change: who, what, when, and that an agent did it.

For your career

The skills that compound

  • Write clear specs for machines. An agent prompt is a requirements doc. Ambiguity shows up as bugs.
  • Think in systems. Decide which steps are deterministic code and which need judgment.
  • Evaluate, don't eyeball. Build a small labeled test set and measure.
  • Own the risk call. Know what an agent may change without asking, and defend that line.
  • Learn the plumbing. APIs, JSON, a little Python. Enough to wire one MCP server yourself.
  • Stay close to people. As the logistics get automated, trust and communication carry more of the job.
