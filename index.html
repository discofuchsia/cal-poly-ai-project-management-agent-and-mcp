The problem

Most TPM work is pulls and pushes.

Pull
  • Status from the tracker
  • PRs and builds from git
  • Decisions buried in chat and docs
  • Dates from five calendars
Decide
  • What to cut when the date is fixed
  • Trade-offs between teams
  • The hard conversation, early
  • Owning the commitment
Push
  • Status to leadership
  • Owner and status changes to the tracker
  • Reminders and follow-ups
  • The report to the docs portal

Agents automate the pulls and pushes. The decision in the middle is still the job.

Anatomy

An agent is a loop of pulls and pushes.

  • Pull: tools read live data from your systems
  • Reason: the model connects what it pulled
  • Push: tools write the result back
  • Approve: a human gates every push

Model Context Protocol

MCP is one standard pipe for every pull and push:
N × M integrations become N + M.

BEFORE · EVERY APP WIRES EVERY TOOL

3 agents × 4 tools = 12 custom integrations

AFTER · EVERYONE SPEAKS MCP

3 + 4 = 7 implementations, and any agent can use any tool

How it works

Hosts, clients, servers

Host

The agent app

Kiro, Claude Desktop, VS Code, your own app. Runs the model and decides when to call a tool.

Client

One per connection

Lives inside the host. Speaks JSON-RPC 2.0 to one server over stdio or HTTP.

Server

Wraps a system

Your tracker, repo, calendar or database. Publishes what the agent may do, with typed inputs.

Tools  pulls like analyze_risks and pushes like update_task

Resources  pulls the app reads in: files, records, schemas

Prompts  reusable templates the user can invoke

Open standard introduced by Anthropic in November 2024 and now supported across many agent hosts. Spec: modelcontextprotocol.io

On the wire

A pull is two JSON messages.

HOST → SERVER

{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "analyze_risks",
    "arguments": {}
  }
}

The model chose this tool because its name, description and input schema came back from tools/list at startup.

SERVER → HOST

{
  "jsonrpc": "2.0",
  "id": 3,
  "result": {
    "content": [{
      "type": "text",
      "text": "{ \"risks\": [ {
        \"severity\": \"high\",
        \"type\": \"dependency\",
        \"task\": \"R-106\",
        \"critical_path\": true
      }, ... ] }"
    }]
  }
}

Under the hood

Pull tools, push tools. About 300 lines of Python.

pm_board_server.py · register a tool

TOOLS = {
  # PULL: reads the board, never changes it
  "analyze_risks": (
    tool_analyze_risks,
    "Deterministic risk scan: blocked, overdue,
     unassigned, blocked dependencies and
     overloaded people, sorted by severity.",
    {"type": "object", "properties": {}}),
  # PUSH: writes to the board
  "update_task": (
    tool_update_task,
    "Change status or assignee, or add a note.
     Writes to the board; ask the human first.",
    {...}),
}
# stdin/stdout loop: initialize, tools/list, tools/call
for line in sys.stdin:
    handle(json.loads(line))

The most important design choice

Pull with code. Reason with the model.
Push with a human.

Pulls · MCP server

Overdue dates, story points, critical path, workload. Deterministic, testable, same answer every run.

Reasoning · model

Which risk matters most, how to say it to an exec, what to put in front of the TPM.

Pushes · TPM approves

Owner changes, status moves, published reports. Nothing is written without a yes.

Ask a model to add up points and it can be confidently wrong. Ask it to explain points a pull added up, and it does that well.

Lessons from running agents on real work

Pulls run free. Pushes earn trust.

1

Pulls automatic, pushes approved

Reads run on their own. Every push shows the exact change and waits for a yes.

2

Cite every pull

Every claim points to the task ID or record it came from, so a reviewer can check it in seconds.

3

Narrow pushes

Expose update_task, not run_sql. Narrow tools are safer and easier for the model to use correctly.

4

Say when the pull is thin

"I don't have enough data" is a valid answer. Make the agent say it instead of guessing.

5

Measure before you trust

Compare the agent's output against answers your experts labeled, before you rely on it.

6

Log every push

Who, what, when, and that an agent did it.

For your career

The skills that compound

  • Write clear specs for machines. An agent prompt is a requirements doc. Ambiguity shows up as bugs.
  • Know your pulls from your pushes. Pulls are cheap to automate. Pushes change what other people see.
  • Evaluate, don't eyeball. Build a small labeled test set and measure.
  • Own the push line. Decide which pushes an agent may make without asking, and defend that line.
  • Learn the plumbing. APIs, JSON, a little Python. Enough to wire one MCP server yourself.
  • Stay close to people. As the logistics get automated, trust and communication carry more of the job.
